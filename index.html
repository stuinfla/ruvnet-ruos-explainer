A computer that acts on its own

ruOS: a desktop that runs itself

ruOS is a real computer, always on, that does not wait for you to click. Ask it to research something, write for you, fix code, or manage itself, and it gets started right away. It is not just a cloud copy of your laptop. It is built to act like a coworker who already has the keys.

You can still watch, or take the wheel, from a browser, an iPad, or a Mac app. But the reason it exists is that it can also go do the work by itself.

Assistants that talk but can't finish the job

What breaks today, and why does it hurt? ›

Even a great AI assistant hits real walls. It cannot click a button by itself. It forgets everything once the chat ends. It can only work on one piece of a big job at a time.

Picture asking an assistant to set up a new app for you. It writes commands and edits files, and gets you most of the way there. Then a window pops up asking you to click 'Next.' The assistant stops. You become its hands, every single time the task leaves the world of text.

Even when there is no window to click, other walls show up. Close the chat and the assistant forgets everything it just learned. Give it five things to do, and it works through them one at a time. It has no way to split the work.

02

A computer with its own team of assistants already inside

What is this thing, concretely? ›

ruOS is a full computer that runs all the time. An AI stack is already installed on it. That stack can split one job across several assistants working at once. It also remembers what it tried before, across sessions. And it can reach out and click, type, and use the screen exactly like a person.

Underneath, it is an ordinary desktop. It has the same screens, windows, and menus you already click through on a laptop. It just happens to run on a machine in the cloud, instead of a box under your desk.

On top of that desktop sits a built-in team. Several assistants can split one job and work on it in parallel. A shared memory survives between sessions. Later work recalls what an earlier session already tried, instead of starting from zero.

A separate control channel lets an attached assistant see the screen, move the mouse, type, and run commands. It can also trigger system actions, like installing or restarting, the same way you would do it yourself.

Right now, one ruOS desktop runs for one operator. A self-serve way to sign up for your own hosted desktop does not exist yet.

03

Why teaching it to click is the clever part

What's the one idea that makes it click? ›

Most programs only talk to a computer through a special connection built just for machines. ruOS skips that step. Its assistant uses the screen, the mouse, and the keyboard the same way a person does.

That means the assistant is not stuck waiting for a program to build it a special doorway in. If a person can open an app, click a menu, or fill in a settings box, the assistant can do the same thing. It works on any program, not just the ones built to expect a machine.

It walks in through the same login you would already use yourself, too. There is no separate machine-only entrance left open on the internet. Whoever can open that login can drive the desktop, and nobody else can.

The assistant doesn't get a fake practice screen or a secret back door — it gets the same mouse, keyboard, and login you'd use yourself.

04

How the control channel actually works

How does it actually work under the hood? ›

The piece that gives an AI client control is a small Rust program, ruos-mcp, that speaks the Model Context Protocol over the desktop's own remote login rather than an open network port.

ruos-mcp talks JSON-RPC 2.0 (a plain request-and-response message format) over stdio (a running program's standard input/output text stream), and that stream is carried inside an ordinary SSH (secure shell — an encrypted remote-login connection) session into the desktop. The security boundary is deliberately simple: whoever can open that SSH session can drive the desktop; nothing here listens on an open network port.

Once connected, the server exposes a fixed catalog of tools: screen capture and mouse/keyboard control built on xdotool and scrot (standard Linux command-line utilities for driving and photographing a desktop); a run_shell tool that runs an arbitrary command and returns its output; and a system_action tool (install / optimize / update / status / restart) that's proxied to a small executor process listening only on the machine's own loopback address.

Two of those tools have a narrower reach than the rest, and it's worth being precise about it: system_action needs that separate executor process running on the desktop, and desktop_resolution needs a further resolution-reporting feature on top of the executor — so on a given desktop, screenshot, mouse, and run_shell are the tools most likely to just work, and the other two are the ones to check for first.

05

What you'd actually use this for

Where would I actually use this? ›

The scenarios below are real things ruOS ships today, run against an actual ruOS desktop.

1 See it, click it, fix it computer use ›

Some installers only offer a graphical dialog, with no command-line option. The assistant can move the mouse, click through it, and type into fields, the same way a person would. Afterward, it can take a screenshot to check the change actually happened, instead of guessing from a command's exit code.

2 Split one job across a team of agents multi-agent ›

A complex, multi-file task can be handed to a swarm instead of one assistant. The swarm starts with a topology — a plan for how agents split and check each other's work — and a cap on how many agents join in. The hierarchical layout is the default, built to keep agents from drifting off task.

3 Pick up where it left off memory ›

An assistant can store a decision or a pattern in memory. Later, a different session can search that memory by meaning, not exact wording, and reuse what already worked instead of rediscovering it.

06

Try it yourself

How do I run it myself, right now? ›

There are two real, working paths today: the assistant team and memory tools (no build needed), and the control channel that lets an assistant drive a ruOS desktop's screen (needs a build and an existing desktop reachable over SSH).

cargo build --release
  1. Check prerequisites You need a Rust toolchain (cargo) to build the control channel, and Node's npx to run the assistant tools. There's no self-serve ruOS signup yet — you point these at a ruOS desktop you already have reachable over SSH.
  2. Try the installed assistant team first Run npx @claude-flow/cli@latest --help and npx ruvector@latest --help. Both fetch on first use, no build and no install, and print the commands for running a multi-agent swarm and a persistent memory store.
  3. Build the control channel From the repo, cd mcp && cargo build --release produces the ruos-mcp binary. A cargo build --release --target x86_64-unknown-linux-musl build gives a statically-linked copy you can drop straight onto the desktop.
  4. Attach Claude Code over SSH claude mcp add ruos -- ssh you@your-ruos-desktop 'DISPLAY=:0 XAUTHORITY=/run/user/1000/gdm/Xauthority /usr/local/bin/ruos-mcp' — the binary runs inside that desktop's own X session, so the connection is an ordinary encrypted login, not an open network port.
  5. What success looks like Ask Claude to screenshot the desktop or run a shell command. You get back an actual PNG image of the screen, or real command output, not a description of one.
  6. What you end up with A Claude Code session that can see and operate a real Linux desktop, split work across the assistant team, and recall memory from earlier sessions, all on one machine you already control over SSH.
  7. Next Read mcp/README.md for the full tool list and desktop-side prerequisites, and skills/README.md for the swarm, memory, and hooks commands.
